## Context

See `proposal.md` for motivation. The constraints that shape this design:

- The app is a **static export** (`next.config.ts`: `output: "export"`) on Firebase Hosting with an SPA rewrite. There is no server, no route handler, and no place to put server-side application code.
- All data access is `supabase-js` -> PostgREST in schema `packmate`. Identity is Firebase Auth; Supabase maps the Firebase uid from the JWT `sub` claim (not `auth.uid()`).
- The `anon` role currently has schema usage but **no table policies**, so anonymous clients can read nothing. That is the baseline this design preserves.
- Trip data is already self-contained: `trip_entries` carries name, qty, `is_packed`, `is_with_me`, description, link, image URL and weight, and `trip_bags` carries nesting via `parent_bag_id`. A trip is already shaped like a shareable snapshot.

## Goals / Non-Goals

**Goals:**

- A visitor with a link sees the current packing list without signing in.
- Anonymous clients never get direct access to the base tables, and the exposed field set is explicit rather than inferred from the schema.
- The owner can see and revoke everything they have shared.
- Add no server, no Functions and no polling; one anonymous read request per view.

**Non-Goals:**

- Collaborative editing, viewer identity, or per-viewer accounts.
- Password-protected links, per-field visibility toggles, or short custom slugs.
- Rich link previews (Open Graph). Crawlers do not run JavaScript and the static export cannot produce per-link HTML. The design stays preview-ready: any future Function would call the same read function.
- Automatic (pushed) updates while a shared page is open.

## Decisions

### Serve public reads through one `security definer` projection function

Add `packmate.share_links` (owner-only RLS) plus a single read function, `packmate.get_shared_trip(p_token text) returns jsonb`, owned by the migration role, `security definer`, fixed `search_path`, no dynamic SQL, `revoke execute from public` then grant to `anon` and `authenticated`.

The function validates the token, short-circuits when there is no active match, then builds one JSON document with `jsonb_agg`: the trip's name and dates, its bags with nesting, and its entries with name, quantity, packed state, location, description, link, image URL and weight.

- Rationale: privacy is **default-closed**. Anonymous clients have no table grants, so a future column on `trip_entries` cannot leak unless someone edits the function. It is one indexed lookup plus one aggregation in a single round trip, so it scales horizontally with no per-viewer state.
- Alternative considered: **RLS policies on `trips`/`trip_bags`/`trip_entries`** gated by a share-token header. Rejected: it grants `anon` the raw table surface, so every schema change silently widens the public API, and it needs three policies instead of one function.
- Alternative considered: **snapshot copy** into a separate public table. Rejected: friends would see stale packing state until the owner re-published, which defeats the point of sharing packing progress, and it adds a refresh concept and a second copy of the data.

### Opaque, high-entropy, server-generated tokens

`share_links.token` is generated by a column default as 256 bits of randomness (`replace(gen_random_uuid()::text || gen_random_uuid()::text, '-', '')`), unique. It is independent of the trip id.

- Rationale: 256 bits makes enumeration infeasible, and the token is not derived from any identifier. Generated in the database so it is never client-controlled.
- Alternative considered: the trip UUID as the secret. Rejected: it cannot be revoked without changing trip identity, and it conflates two concepts.

### One active link per trip; regenerate mints a new token

A partial unique index `unique (trip_id) where revoked_at is null` enforces one active link per trip. Sharing a trip that already has an active link returns it. Regenerating revokes the current row and inserts a new one with a fresh token.

- Rationale: a revoked URL can never come back to life by un-revoking the same row, which is what would happen if regenerate reused the token.
- Alternative considered: many named links per trip. Rejected as unused complexity for a consumer app; the schema can relax the index later without a data migration.

### Soft revoke plus optional expiry, with an indistinguishable unavailable state

`share_links` has `revoked_at timestamptz null` and `expires_at timestamptz null`. The read function requires `revoked_at is null` and `(expires_at is null or expires_at > now())`. Every non-match (unknown, revoked, expired, deleted trip) returns `null`, and the page renders one generic unavailable state.

- Rationale: revocation is immediate, the owner keeps history, and the endpoint cannot be used as an oracle for which tokens exist. Deleting a trip cascades to its links, so a dead trip cannot leave a live link.
- Alternative considered: hard delete on revoke. Rejected: loses the owner-visible history and the "revoked" status the management page shows.

### Manual refresh instead of realtime or polling

The shared page fetches on load and exposes a refresh control. It does not open a Realtime channel and does not poll.

- Rationale: `AGENTS.md` calls long-lived listeners and polling cost traps, and Realtime would require an anonymous subscription path that RLS does not cover.
- Alternative considered: Supabase Realtime. Rejected for cost and authorisation complexity; revisit only if collaborative editing is ever specified.

### Read-only presentation is extracted, not forked

The shared page reuses the existing pure helpers in `lib/packing.ts` (`buildBagTree`, `groupEntries`, `packingProgress`, `entryLocationPath`) and extracts a read-only presentational component from the trip view. The interactive trip page keeps its own mutation wiring.

- Rationale: the grouping and weight rules must match the trip view exactly; duplicating them would drift. Extracting the presentation layer also follows the project's composition guidance.
- Alternative considered: rendering the shared list from the trip page component directly. Rejected: the trip page is large and coupled to mutation and drag-and-drop state.

### No backend; no link previews

No Firebase Function, no API route, no Supabase Realtime. The only server-side code is the Postgres function. `functions/` stays limited to the auth blocking hooks.

- Rationale: nothing here needs a server. Previews are the only feature that would, and they would also require a URL path owned exclusively by a Function (the static `out/share.html` wins over a Hosting rewrite under `cleanUrls`), which is a separate structural decision.
- Alternative considered: a Function to serve Open Graph tags. Deferred; the read function is reusable if it is ever added.

### Token travels in the query string

The canonical URL is `/share?t=<token>`.

- Rationale: static export cannot build a dynamic `[token]` route at build time, and the trip page already uses `/trip?id=`. A URL fragment (`#t=`) would keep the token out of Hosting logs and browser history and remains an available hardening step, but it can be dropped by some redirect chains.

### Security headers and exposure set are part of the feature

The share page sets `noindex, nofollow` and a `no-referrer` referrer policy, and every external item link uses `rel="noopener noreferrer"`. Exposed fields: trip name and dates, bag names and nesting, entry name/quantity/packed state/location, description, link, image URL, weights and bag limits. Never exposed: `user_id`, `source_item_id`, `source_bag_id`, `profiles`, or any other trip.

- Rationale: without `no-referrer`, following an item's external link would leak the share token to a third party. `description` is included by owner decision; the owner's display name is deliberately excluded because it is often a real name set for account purposes.

### Accept volumetric abuse; do not build rate limiting

The `anon`-callable function is publicly reachable, so it can be flooded. Tokens are unguessable, so the exposure is cost and availability, not data. The function short-circuits on a non-match before aggregating, and view tracking is omitted so no anonymous read causes a write.

- Rationale: Supabase provides no WAF or per-IP limiting on the target plans; a Postgres-side limiter would add a write per anonymous read, the exact cost trap to avoid. Mitigation is a cheap read plus monitoring, with an edge proxy (for example Cloudflare) held in reserve if it is ever targeted.

### Include share links in the data export

`collectUserData` returns share links and the export type gains a `share_links` field.

- Rationale: links are the user's data and the export promises all of it. Account deletion already removes them through the trip cascade.

## Risks / Trade-offs

- **`security definer` is privileged code.** A bug that ignored the token would serve any trip -> keep the function minimal and reviewable, keep `anon` off the base tables, and add an integration test proving the function returns nothing without a valid, active token.
- **Confidentiality-by-URL.** Anyone with the link can read it, and it can leak through chats, screenshots, history or logs -> revocation, optional expiry, `noindex` and `no-referrer` are the controls; the exposure is accepted for packing-list data, which contains no addresses or personal identifiers.
- **Live sharing publishes new entries immediately.** A newly added item is visible without a review step -> revoke and expiry are the remedies; a publish gate was rejected because it reintroduces staleness.
- **Volumetric abuse.** The anonymous endpoint can be flooded -> keep the read cheap, monitor usage, add an edge proxy later if needed. Recorded as a conscious decision.
- **No rich previews.** Shared links will unfurl as a plain URL in chat apps -> accepted; a Function-based preview is a separate change and the read function is reusable.
- **Token in the query string** appears in Hosting logs and history -> high entropy plus revocability limits the impact; the fragment is the fallback hardening step.
- **`cleanUrls` versus a future preview path.** If previews are added, they need a path the static export does not claim -> that change must choose a separate URL shape; it does not affect this design.

## Migration Plan

1. Apply one additive migration: create `packmate.share_links` with owner-only RLS and indexes, the partial unique index on active links, and the `get_shared_trip` function with grants. No existing table, policy or row is modified.
2. Ship the frontend: `/share` public page, `/shares` management page, trip Share action, extracted read-only view, export addition.
3. Rollback: drop the function and table. Existing trips, bags and entries are untouched, so rollback restores the prior behaviour with no data loss.
