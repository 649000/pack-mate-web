## Context

See `proposal.md` for motivation and `specs/trips/spec.md` for the behavior contract.

Relevant current state:

- A trip owns `trip_bags` and `trip_entries`, both `on delete cascade` from `trips` (`supabase/migrations/20260914000000_packing_list_foundation.sql:61`).
- `trip_bags` carries `source_bag_id`, `position`, `weight_limit_grams` and, after nested containers, `parent_bag_id`.
- `trip_entries` carries `source_item_id`, `is_with_me`, `is_packed`, `position`, `description`, `link`, `image_url`, `weight_grams` and `category`.
- The existing copy pattern is `add_library_bag_to_trip`, a `security invoker` function that verifies ownership and copies library rows into a trip (`:329`).
- The trips list already hosts the create/edit trip dialog with name, country, destination and date fields (`app/(app)/trips/page.tsx:317`).

## Goals / Non-Goals

**Goals:**

- Duplicate a trip's packing list atomically, with correct bag/entry id remapping.
- Keep the new trip's trip-level fields under the user's control at duplicate time.
- Guarantee the copy is independent and that ownership is enforced by RLS.

**Non-Goals:**

- Linking the copy to the source for future sync.
- Copying share links or packed state.
- Bulk library selection or bulk pack/unpack (separate changes).
- Any new trip-level field.

## Decisions

### One atomic `security invoker` function

`duplicate_trip(p_source_trip_id, p_name, p_country_code, p_destination, p_start_date, p_end_date)` creates the trip and copies its bags and entries in a single transaction, returning the new trip id.

- Rationale: the copy spans three tables and remaps foreign keys. A transaction means a failure or cancel leaves nothing behind, and avoids an orphan empty trip.
- Alternative considered: `createTrip` followed by client-side inserts. Rejected: non-atomic, many round trips, and it leaves a half-built trip on failure.

### Remap bag ids with a two-pass insert

Insert all copied bags with `parent_bag_id` null while recording an old-id to new-id map, then set `parent_bag_id` from the map in a second pass.

- Rationale: parent ids are generated by the insert, so nesting cannot be expressed in one pass. A two-pass map is simple and order-independent.
- Alternative considered: topological insert order. Rejected as more code for no benefit.

### Trip-level fields come from the prompt, not the source

The function takes the new trip's name, country, destination and dates as parameters; the client prefills name/country/destination from the source and leaves dates empty.

- Rationale: the new trip is a new occasion. Prefilled-but-editable defaults save typing without copying stale dates that would show a false countdown.
- Alternative considered: copy the source row and let the user edit afterward. Rejected: it creates a wrong trip first and requires a second edit pass.

### Preserve provenance, reset state

Copied rows keep `source_item_id` and `source_bag_id` (nullable, `on delete set null`), and every entry is inserted with `is_packed = false`; `is_with_me` and positions are preserved.

- Rationale: provenance stays useful and library edits still do not propagate; packed state is inherently about the new occasion.
- Alternative considered: null out provenance. Rejected: loses information for no gain.

### Ownership enforced in the function and by RLS

The function is `security invoker` and first asserts the source trip's `user_id` matches the caller, mirroring `add_library_bag_to_trip`; RLS insert policies on `trip_bags` and `trip_entries` continue to scope rows by trip ownership.

- Rationale: never trust a client-supplied trip id; the database is the authority.
- Alternative considered: app-side ownership check only. Rejected as insufficient.

## Risks / Trade-offs

- **Nested bag remap mistakes** → two-pass old/new id map, covered by integration tests that duplicate a trip with nested bags.
- **Partial copy on failure** → single transaction; the function raises and rolls back.
- **Duplicate trip names** → no unique constraint exists; the client defaults to `<name> (copy)` but the system allows duplicates, which is acceptable and matches create.
- **Empty trip** → duplicating a trip with no bags or entries creates a trip with an empty list, which is valid.
- **Long lists** → the copy is a set of set-based inserts inside one function, not per-row round trips, so it stays cheap.

## Migration Plan

1. Add a migration creating `packmate.duplicate_trip(...)` and granting execute to `authenticated`.
2. Add `duplicateTrip` to `lib/data.ts` calling the function.
3. Add the Duplicate action and prompt to the trips list and trip page header.
4. Rollback: drop the function; the UI action is removed with the deploy.
